1项目概览

Algocode 是一款可验证的算法优化 Agent CLI 工具，面向 C++ 和 Python 项目。它不是直接替你改代码的黑盒，而是通过行为契约、隔离 Worktree、三层证据验证来驱动代码优化。

核心定位

Algocode 读取 Git 仓库和项目入口，通过具备工具调用能力的 Agent 分析算法热点、问题结构和复杂度，在隔离的 Git Worktree 中生成候选实现。Agent 可以读取完整文件、搜索代码库、运行构建与正确性测试、执行 Benchmark，从而进行算法级优化，而不只停留在表面代码改写。

核心理念
每个候选都必须通过 Correctness（正确性）、Contract（契约）和 Benchmark（基准测试）三层验证。用户查看结构化证据链、Diff、置信区间和决策结果后，显式执行 accept 和 apply。应用后如果发现问题，还可以通过 rollback 回滚。

2为什么需要 Algocode

通用 AI Agent 在做算法优化时存在系统性缺陷。Algocode 的每一个设计决策都对应解决一个具体痛点。

通用 Agent 的局限

  • 只能改代码，不能证明正确性 — 模型可能改变边界条件、错误语义、返回顺序或状态转换
  • 容易只做局部优化 — 倾向于修改循环和变量，不主动重新分析问题结构
  • 性能结果缺少可信依据 — 单次 time 受系统负载、缓存、解释器启动影响
  • 长任务容易偏离目标 — 上下文增长后忽略行为契约和验证约束
  • 缺少候选生命周期 — 没有隔离候选、证据门控和回滚机制
  • 难以比较不同方向 — 多个方案只存在于对话中，无法系统比较
  • 过程难以审计 — 为什么接受/拒绝没有完整记录
  • 质量依赖模型和提示词 — 换模型结果明显波动

Algocode 的解决方案

  • 行为契约先行 — 优化前明确 API、输入输出、错误行为、状态转换、排序和边界
  • 算法级分析 — 分析问题结构、输入分布、操作代数和复杂度差距
  • 可信 Benchmark — warmup、重复采样、交错运行、多规模输入、固定 harness
  • 阶段门禁约束 — 每阶段只暴露允许工具，持续告知预算和自检要求
  • 隔离候选 + 回滚 — Git Worktree 隔离，Apply 后可 Rollback
  • 多候选搜索归档 — Top+Diverse 策略选择，系统比较性能和风险
  • 完整证据链 — Contract、Correctness、Benchmark、Decision、模型日志全持久化
  • 模型可替换 — 复用相同的契约、验证、Benchmark 和候选生命周期

Bootstrap 依赖注入

bootstrap.py 中的 build_context() 按依赖顺序组装所有服务，形成一个 AppContext 容器：

  1. 基础设施：AlgocodeConfig → SecretRedactor → Database(SQLite) → 8 个 Projections → SqliteEventStore → SandboxProcessRunner → LanguageRegistry → FileArtifactStore → PolicyEngine → ApprovalService → LocalProcessSandbox
  2. 服务层（按依赖顺序）：TaskService → ProjectService → BaselineService → CorrectnessService → BenchmarkService → CandidateService → ResourceProvider → DecisionService → ExperimentService → SearchArchiveService → MaintenanceService → ApplyService → ReportService → ToolRegistry

所有服务共享同一个 SqliteEventStore，事件按 aggregate_id 分片；服务间通过直接注入依赖实现松耦合。

4.3 工具循环（Tool Loop）

每个阶段内部的工具循环是一个受约束的 LLM 驱动循环。_run_phase() 的核心流程：

for _ in range(max_steps_per_phase):  # 默认 30 轮
    1. 检查 cancel_event
    2. 获取任务状态
    3. 构建上下文摘要 # project/baseline/candidate/evidence
    4. 注入当前阶段指令 # 含预算提示
    5. 更新 Facts 账本
    6. 构建 ContextSnapshot # 写入 EventStore
    7. 调用 LLM # _complete_model()
    8. 处理响应：
       - 无 tool_calls → 可能是最终提交
       - 有 tool_calls → 逐个执行
    9. 记录 AGENT_TURN_COMPLETED
    10. 检查阶段自动完成条件
    11. 检查终止条件（无进展/验证失败/超时/上下文溢出）

4.4 阶段工具白名单

每个阶段只暴露允许使用的工具，降低模型误用风险：

4.5 预算控制体系

⏱️

模型轮次预算

每阶段最多 30 轮模型调用（max_steps_per_phase）。每轮记录 AGENT_TURN_STARTED/COMPLETED 事件。

🔧

工具调用预算

每阶段最多 50 次工具调用（max_tool_calls_per_phase）。超出时返回 tool call budget exhausted。

🔬

修改检查约束

每 4 次代码修改（MAX_MUTATIONS_BEFORE_CHECK=4）后必须调用 run_candidate_check，防止无限修改不验证。

预算信息不仅用于运行时控制，还通过 _with_budget_instruction() 注入 LLM 上下文，让模型在调用工具前知道剩余轮次和工具调用次数。

4.6 自动完成机制

阶段不依赖模型主动提交，而是根据工具执行结果自动判断完成：

自动完成触发条件

  • GENERATE_CANDIDATE：create_candidate 成功
  • VERIFY：run_correctness + run_contract（如有）通过
  • BENCHMARK：run_benchmark 产生有效证据
  • ANALYZE：ReadCoverage.complete（必需文件在 ≥2 轮中被读取）

防偏离机制

  • 防重复：相同 tool call signature 连续出现 3 次 → STOP REPEATING
  • 防协议错误：连续 3 次无效工具参数 → 阻塞阶段
  • 上下文溢出：最多重试 2 次，每次缩放到 70%
  • 修复记忆：check 失败后只允许修补工具

4.7 重试与恢复

Algocode 支持基于历史记录的多候选搜索和重试：

  • 多候选搜索：当一个方向有显著正向前景但尚未满足接受条件时，继续细化同一候选（refine）；当方向没有可测收益时，基于历史创建新候选继续搜索（pivot）。
  • RetryDecision：支持 continue（继续同方向）、pivot（切换新方向）、rollback（回退到父候选尝试不同子步骤）三种模式。
  • 跨运行恢复：从 EventStore 倒序读取 ANALYSIS_COMPLETED 和 PLAN_COMPLETED 事件，恢复已完成的阶段。
  • OptimizationRecordStore：每次运行写入 JSON + Markdown 持久化记录，支持 render_history() 生成重试上下文。

4.8 修复记忆（Repair Memory）

修复记忆机制
当 run_candidate_check 失败时，系统会记录失败的证据（summary、structured）、变更文件列表、diff（截取 20000 字符），并通过 RepairMemoryStore.render_brief() 生成修复上下文注入后续 LLM 请求。同时设置 repair_patch_required=True，后续工具调用只允许 apply_patch、write_file、edit_file，防止重复只读检查循环。

5三层验证体系

Algocode 将优化结果拆成三类证据：Correctness（正确性）、Contract（契约）和 Benchmark（基准测试）。优化速度和正确性发生冲突时，正确性优先。

✓

Correctness 正确性

验证候选是否复现基线行为。支持 cases、oracle、stress、hybrid 四种模式。

📋

Contract 契约

保护公开 API、配置语义、错误类型、状态转换、排序和边界行为。Contract Test 在保护目录中运行。

📊

Benchmark 基准测试

受控测量 warmup、重复采样、median、variation、环境 hash。交错运行基线与候选减少噪声。

5.1 正确性验证 — 四种模式

模式机制适用场景
CASES预定义输入 + 预期输出，逐 case 验证已知测试用例
ORACLE运行候选，用 oracle_command 生成预期输出并比较有参考实现可生成预期
STRESSgenerator_command 生成随机输入，迭代 N 次（递增 seed），oracle 验证需要大规模随机测试
HYBRID同时支持 cases + oracle混合验证策略

比较模式

模式逻辑
EXACT直接字节比较
LINE_TRIM逐行 rstrip 后比较
TOKEN_NORMALIZED空白 token 统一为单空格
FLOAT_ABSOLUTE解析为 float，绝对差比较
FLOAT_RELATIVE相对误差比较，使用 float_tolerance
CHECKER_COMMAND自定义 checker 脚本，exit 0 为通过

保护文件检查

find_protected_changes() 在正确性运行前检查变更文件列表。默认保护文件包括 tests/、.algocode/oracle/、.algocode/benchmarks/、.algocode/config.yaml、.algocode/contract.json 等。保护文件被修改会直接构造 PROTECTED_FILE_CHANGED 级别的失败。

5.2 Benchmark 引擎

采样流程

# 单目标采样
for each input_case:
    warmup 轮  # 默认 5 轮，不记录
    repeats 轮  # 默认 15 轮，记录为 BenchmarkSample

# 交错采样（Baseline vs Candidate）
Baseline warmup → Candidate warmup
Baseline measured → Candidate measured  # 交替执行
# 由 index % 2 控制顺序，减少机器状态漂移

统计汇总

summarize_values() 输出丰富的统计指标：

指标说明
median中位数（主要比较指标）
mean / stddev均值与总体标准差
variation_percent变异系数
robust_variation_percent基于 MAD 的鲁棒变异率
ci_lower / ci_upperBootstrap 置信区间
trimmed_medianIQR 过滤异常值后的中位数

比较与统计显著性

compare_sample_sets() 支持：

  • 独立比较与配对比较
  • 每 input case 的 baseline/candidate median / improvement_percent
  • 置换检验 p_value
  • Bootstrap CI
  • 变差超过 max_variation_percent（默认 15%）时标记 invalid
  • estimate_growth()：拟合 log(value) = exponent × log(size) + intercept，输出 GrowthEstimate（exponent、points、r_squared），用于识别算法级改进

环境一致性

环境哈希校验
候选体工作区环境哈希必须与基线一致，否则 BenchmarkService 拒绝运行。这确保 Benchmark 结果的可比性。同时使用 FileResourceLock 按 benchmark:{environment_hash} 加锁，保证并发下同一环境不会并行干扰。

6.1 项目初始化（Bootstrap）13 阶段

ProjectBootstrapService.run() 的完整流程：

  1. Git 初始化 — discover 或 initialize
  2. 语言检测 — 通过 LanguageRegistry 检测 Python/C++
  3. Contract 发现 — 向 LLM 发送带 schema 的请求，生成 ProjectContract
  4. Contract 编译 — 持久化 contract JSON，复制 reference sources，生成 contract test
  5. Contract 测试 — 执行 contract_test.py/.cpp，失败则重试最多 3 次
  6. Fallback — 若仍失败，切换到 reference conformance test
  7. Spec 生成 — 生成 correctness.yaml、benchmark.yaml、harness.py
  8. Benchmark 校准 — 双探针法计算 repeat count（CALIBRATION_ROUNDS=200, STEPS=4, TARGET=0.5s）
  9. Project 注册 + Task 创建
  10. Baseline 捕获
  11. Correctness 验证 — 失败则 fallback
  12. Benchmark 验证 — 多尺度失败则回退单输入
  13. 持久化状态 — 写入 current-task.json 和 task.txt

6.2 Stale 保护机制

ApplyService 在 apply 前校验当前 git snapshot 与 apply 时的快照一致。如果不一致（用户在优化期间手动修改了代码），候选体被标记为 STALE 并拒绝应用。这防止了基于过时基线的优化覆盖用户的手动更改。

6.3 多候选搜索归档

SearchArchiveService 使用 Top + Diverse 策略选择历史候选条目：

  • 仅包含 Correctness 通过且有 Decision 的候选
  • 先按 improvement_percent 降序选取 Top 条目
  • 再按 patch_hash/candidate_id 选择 Diverse 条目，直到达到 max_population（默认 6）
  • 输出格式：candidate {id} (parent={parent}, outcome={outcome}, improvement={improvement}%): {reason}

7领域模型与事件溯源

Algocode 采用不可变领域模型 + 事件溯源（Event Sourcing）架构。所有状态变更通过事件持久化，通过 Projection 读取当前状态。

7.1 核心实体

Project

id（确定性，基于根路径 SHA256）、root_path、name、language、git_revision

Task

id、project_id、objective、status、current_phase、baseline_id、active_candidate_id

Candidate

id、task_id、base_revision、workspace_ref、status、patch_hash、parent_candidate_id（支持 fork 树）

  → COMPARISON_PRODUCED → EXPERIMENT_COMPLETED
  → DECISION_MADE (ACCEPTED)
  → CANDIDATE_APPLIED
  → REPORT_GENERATED → TASK_COMPLETED

# 失败路径
  → BASELINE_FAILED / CORRECTNESS_FAILED
  → DECISION_MADE (REJECTED)

7.4 SQLite 持久化

  • WAL 模式：PRAGMA journal_mode = WAL
  • 外键约束：PRAGMA foreign_keys = ON
  • 忙等超时：PRAGMA busy_timeout = 5000
  • 乐观并发：append() 使用 BEGIN IMMEDIATE，检查 expected_seq 防止并发冲突
  • 8 个 Projection：Task、Project、Baseline、Correctness、Benchmark、Candidate、Decision、Experiment

9工作区与 Git 集成

Algocode 使用 Git Worktree 实现 Baseline 和 Candidate 的隔离。所有优化在独立工作区中进行，验证通过前不会修改用户项目。

9.1 Workspace 类型

BASELINE Workspace

从 Git root 或 source workspace 捕获快照，创建 detached worktree。用于基线构建、正确性验证和 Benchmark。

CANDIDATE Workspace

基于 Baseline 或父 Candidate fork 创建。Agent 在此工作区中修改代码，运行验证。路径：.algocode/cache/worktrees/candidate/<task_id>/<workspace_id>

9.2 Snapshot 与哈希

RepositorySnapshot 包含 revision、patch、untracked 文件和 snapshot_hash。哈希计算覆盖 revision、patch 内容、untracked 文件路径/类型/内容，生成 SHA256。这确保任何文件级变更都能被检测到。

9.3 Apply 流程

1. 校验 candidate 属于该 task
2. 校验 decision = ACCEPTED
3. 校验 candidate 未被应用过
4. 校验 baseline 存在
5. Stale check：当前 git snapshot 必须等于 apply_base_revision + apply_base_snapshot_hash
6. 捕获 candidate workspace 的 patch → 保存为 artifact
7. GitWorkspaceManager.apply() 将 patch 应用到项目仓库
8. 重建 untracked 文件
9. 写入 rollback manifest
10. emit CANDIDATE_APPLIED

9.4 Rollback 流程

1. 读取 rollback manifest
2. 检查当前仓库 snapshot hash 是否与 apply 时一致
3. 若有 patch → git apply --reverse
4. 删除创建过的 untracked 文件
5. 删除 manifest
6. emit CANDIDATE_ROLLED_BACK

17安全与数据保护

Algocode 在多个层面实施安全防护，从凭证存储到日志脱敏到沙箱隔离。

🔐

凭证存储

API Key 保存在本机凭证文件中，不写入项目配置。支持 env:// 和 local:// 两种引用方式。

🕵️

18核心设计哲学总结

Algocode 的每一个架构决策都服务于同一个目标：让算法优化有证据、可审计、可回滚。

1. 契约先行

优化前明确公开 API、输入输出、错误行为、状态转换、排序和边界条件。禁止通过删除检查或修改测试获得性能提升。契约是硬约束，不是建议。

2. 证据驱动

不依赖模型自我评价。每个候选必须通过 Correctness、Contract 和 Benchmark 三层验证。正确性与速度冲突时，正确性优先。

3. 隔离与回滚

Git Worktree 隔离 Baseline 和 Candidate。Apply 前检查 stale。Rollback 通过 manifest 和 git apply --reverse 恢复。用户显式控制 accept 和 apply。

4. 阶段门控

11 个阶段严格按序执行，阶段间 Gate 检查前置条件。每阶段只暴露允许工具。阶段自动完成不依赖模型主动提交。

5. 可信 Benchmark

Warmup + 重复采样 + 交错运行 + 多规模输入 + 固定 harness。配对置换检验 + Bootstrap CI + MAD 鲁棒波动。区分真实收益与随机波动。

6. 模型可替换

支持 10+ Provider，统一接口。契约、验证、Benchmark 和候选生命周期与模型无关。换模型不换验证体系。

7. 事件溯源

所有状态变更通过 EventEnvelope 持久化到 SQLite。8 个 Projection 提供读模型。乐观并发控制。完整审计追踪。

8. 预算感知

模型轮次、工具调用、成本预算三层控制。预算信息注入 LLM 上下文，让模型自我约束。防重复、防偏离、修复记忆。

一句话总结
Algocode 不是一个替你改代码的黑盒——它是一个建立行为契约、在隔离环境中尝试优化、用三层证据决定候选是否值得应用的可验证算法优化 Agent。
